# Internationalization

Supported languages: **Spanish (`es`, default)** and **English (`en`)**.

There are two independent kinds of translation:

1. **Interface translation** — buttons, navigation, validation messages, emails. Stored
   in the repository as message files, required to be complete in both languages.
2. **Course content translation** — course titles, lesson descriptions, video audio and
   subtitles. Stored in the database, and may legitimately exist in only one language.
   See [content-model.md](content-model.md).

A student can use the interface in English while taking a course that only exists in
Spanish. The UI must say which languages a piece of content is available in, and must
never machine-translate or invent missing content.

## Web (`apps/web`, next-intl)

- Messages: `apps/web/messages/{es,en}.json`, namespaces `common`, `navigation`, `home`,
  `auth`, `dashboard`, `courses`, `lessons`, `subscriptions`, `profile`, `validation`,
  `errors`, `designSystem`, `metadata`. Placeholders use ICU syntax (`{min}`).
- Routing: `src/i18n/routing.ts` defines locales and **localized pathnames**. Every URL
  is prefixed with the locale:

  | Page | Spanish | English |
  | --- | --- | --- |
  | Home | `/es/` | `/en/` |
  | Catalog | `/es/cursos/` | `/en/courses/` |
  | Course | `/es/cursos/{slug}/` | `/en/courses/{slug}/` |
  | Lesson | `/es/cursos/{slug}/lecciones/{lesson}/` | `/en/courses/{slug}/lessons/{lesson}/` |
  | Log in | `/es/iniciar-sesion/` | `/en/login/` |
  | Sign up | `/es/registro/` | `/en/register/` |
  | Dashboard | `/es/dashboard/` | `/en/dashboard/` |
  | Profile | `/es/perfil/` | `/en/profile/` |

  Because the site is a static export, each localized path is a physical route folder
  under `src/app/[locale]/` pinned to one locale with `generateStaticParams` +
  `dynamicParams = false`. Page components live once in `src/features/*` and are
  re-exported by both folders.
- `/` has no server to negotiate the language, so it renders a tiny page that redirects
  on the client to the stored preference, then the browser language, then `/es/`
  (with a `<noscript>` meta refresh to `/es/`).
- **Language switcher** (`src/components/language-switcher.tsx`): maps the current page
  to the same page in the other locale (including dynamic segments), stores the choice in
  `localStorage` (`top-dance.locale`) and a `NEXT_LOCALE` cookie, then navigates. The
  query string is preserved.
- SEO: `<html lang>`, canonical URLs and `hreflang` alternates on every page
  (`src/lib/metadata.ts`); localized 404 pages per locale.
- Validation: Zod schemas are created with a translator (`createLoginSchema(t)`), so error
  messages come from the `validation` namespace.
- Tests (`pnpm --filter @top-dance/web test`): es/en key parity, placeholder parity,
  routing config, locale preference resolution.

## Mobile (`apps/mobile`, i18next)

- Messages: `apps/mobile/src/i18n/locales/{es,en}.json`. Keys are the **same keys as
  the web** (a test fails if a shared key's text differs from the web message); keys that
  only make sense on mobile live under the `mobile` namespace.
- Interpolation is configured to `{name}` so placeholders match the web.
- Language resolution: stored manual choice (AsyncStorage `top-dance.locale`) →
  device language (`expo-localization`) → `es`. The Profile tab lets the user pick
  Spanish, English or "device language".
- `app.json` declares `supportedLocales` so iOS/Android show the per-app language setting.

## API (`apps/api`, Rails I18n)

- `config.i18n.available_locales = [:es, :en]`, default `:es`.
- API requests: `?locale=` → `Accept-Language` (quality-sorted) → `es`; the response
  carries `Content-Language`. `GET /api/v1/locales` lists supported languages.
- ActiveAdmin and Devise screens are translated (`devise-i18n`, `config/locales/*.yml`);
  admins switch with `?locale=en`, remembered in the session.
- I18n fallbacks are **not** used for course content: a missing translation must stay
  visible as missing.
- Planned: `users.preferred_locale` to localize emails and push notifications.

## Adding a string

1. Add the key to **both** `es.json` and `en.json` (web, and mobile if used there).
2. Use it via `useTranslations("namespace")` / `getTranslations` on web, `t("ns.key")` on mobile.
3. Run the tests; parity tests fail on missing keys.
